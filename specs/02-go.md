# 規格 02：Go 程式改寫（G1–G4）

> 先讀 [README](README.md)。
> **開始前先問使用者**：Go 的部分要自己打，還是由你套用參考實作後逐段講解。原計畫是由 AI 寫。
> 參考實作在 `specs/_reference/go/`，路徑和 repo 一一對應，已通過 `go build ./...` 和 `go vet ./...`。

## 設計原則

- 用環境變數 `PLATFORM` 切換：`k8s`（預設）或 `cloudrun`。**不設定時行為和現在完全一樣**，K8s 版不受影響。
- Engine 的 controller 只依賴 `Launcher` 介面，不知道底下是哪個平台。
- K8s 相關的程式碼只搬動和包一層，不改邏輯。

## 現有程式的狀況

| 檔案 | 現況 |
|---|---|
| `common/config/config.go` | `EngineConfig`、`CleanerConfig`，用 `getEnv` 系列函式讀環境變數 |
| `services/engine/service/launcher.go` | `JobLauncher`，`CreateJob` 回傳 `*batchv1.Job`，每次請求都讀 ConfigMap 取配額 |
| `services/engine/controller/run.go` | 直接依賴 `*service.JobLauncher`，所有錯誤都回 500 |
| `services/engine/router/router.go` | 已經有 `gin.SetMode(gin.ReleaseMode)` 和 `SetTrustedProxies(nil)`，不用再處理 |
| `services/cleaner/service/cleaner.go` | 常駐輪詢，收割卡在異常 Waiting 狀態的 Pod |
| `go.mod` | `go 1.25.0`，module 名稱 `sep` |

## G1：設定、介面、K8s launcher 改名

| 動作 | 檔案 | 說明 |
|---|---|---|
| 覆蓋 | `common/config/config.go` | `EngineConfig` 加 `Platform`、`GCPProject`、`GCPRegion`、`TaskServiceAccount`、`SystemQuotasJSON`、`AllowedImagePrefixes`；`CleanerConfig` 加 `Platform`、`GCPProject`、`GCPRegion`、`JobRetention` |
| 新增 | `common/model/labels.go` | Engine 和 Cleaner 共用的 label 常數 |
| 改名並修改 | `services/engine/service/launcher.go` → `k8s_launcher.go` | 用 `git mv` 保留歷史。只新增一個 `Launch` 方法包住原本的 `CreateJob`，其他不動 |
| 新增 | `services/engine/service/launcher.go` | `Launcher` 介面和 `ErrRejected` |
| 覆蓋 | `services/engine/controller/run.go` | 改成依賴 `service.Launcher`；`errors.Is(err, service.ErrRejected)` 時回 400 並告知原因 |
| 覆蓋 | `services/engine/router/router.go` | `SetupRouter(launcher service.Launcher)`，移除沒用到的 `cfg` 參數 |

新增的環境變數：

| 變數 | 用在 | 預設 | 說明 |
|---|---|---|---|
| `PLATFORM` | 兩者 | `k8s` | `k8s` 或 `cloudrun` |
| `GCP_PROJECT`、`GCP_REGION` | 兩者 | 空 | Cloud Run 模式必填 |
| `TASK_SERVICE_ACCOUNT` | Engine | 空 | 任務容器的身分（`sep-task` 的 email） |
| `SYSTEM_QUOTAS_JSON` | Engine | `{}` | 例：`{"demo-go":{"cpu":"1","memory":"512Mi"}}` |
| `ALLOWED_IMAGE_PREFIXES` | Engine | 空 | 逗號分隔。空的話 Cloud Run 模式會拒絕啟動 |
| `JOB_RETENTION` | Cleaner | `5m` | 任務 job 跑完後保留多久 |

`PORT` 不用處理：Cloud Run 會自動注入 `PORT=8080`，Engine 本來就讀這個變數。

## G2：`CloudRunLauncher`

新增 `services/engine/service/cloudrun_launcher.go`，覆蓋 `services/engine/main.go`。

**`Launch` 的流程**

1. 驗證，不通過就回傳包著 `ErrRejected` 的錯誤（controller 回 400）：
   - `system_id` 符合 `^[a-z0-9]([-a-z0-9]*[a-z0-9])?$`（它會成為 job 名稱的一部分）。
   - `system_id` 在配額表裡。
   - `image` 以白名單中某個前綴開頭。
2. `CreateJob`：job ID 為 `job-<system_id>-<unix 毫秒>`。這是長時間操作，用 `op.Wait` 等它完成，上限 60 秒。
3. `RunJob`：送出執行請求就回傳，**不等任務跑完**。
4. 回傳 job ID。

**Job 的設定**

| 欄位 | 值 | 對應 K8s 版 |
|---|---|---|
| Labels | `managed-by=sep-engine`、`system_id`、`task_id` | `app.kubernetes.io/managed-by` 等 |
| `MaxRetries` | 0 | `backoffLimit: 0` |
| `ServiceAccount` | `TASK_SERVICE_ACCOUNT` | Pod 的 ServiceAccount |
| `Resources.Limits` | 配額表的 `cpu`、`memory` | `resources.limits`（Cloud Run 沒有 request） |
| `Image`、`Command` | 來自請求 | 相同 |

**值得講給使用者聽的設計點**

- 配額表在啟動時載入一次。K8s 版每次請求都讀 ConfigMap，這裡順便解決了。代價是改配額要重新部署（`terraform apply` 會產生新 revision）。
- GCP 的 label key 不能有 `/` 和 `.`，所以用 `managed-by` 而不是 `app.kubernetes.io/managed-by`。label 值只能是小寫英數、`_`、`-`，所以 `task_id` 要先經過 `sanitizeLabel`。
- image 白名單是這個版本新增的防護：Engine 有權限建立 job，如果有人能呼叫 Engine，白名單限制了他能跑的東西。
- 憑證：`run.NewJobsClient(ctx)` 不帶任何金鑰，在 Cloud Run 上自動使用 `sep-engine` 這個身分，在本機使用 ADC。
- `RunJob` 失敗時 job 已經建立但沒有執行，會留下孤兒，由 Cleaner 回收（見 G3）。

**`main.go`**：`switch cfg.Platform`，`cloudrun` 建 `CloudRunLauncher`，`k8s` 建原本的 `JobLauncher`，其他值直接 `log.Fatalf`。Cloud Run 模式下不初始化 K8s client。

## G3：`CloudRunCleaner`

新增 `services/cleaner/service/cloudrun_cleaner.go`，覆蓋 `services/cleaner/main.go`。原本的 `cleaner.go` 不動。

**職責和 K8s 版不同**：K8s 版收割的是卡住的異常 Pod；Cloud Run 版取代的是 `ttlSecondsAfterFinished`，刪除已經跑完的 job，因為 Cloud Run Job 不會自己消失。

**`RunOnce` 的流程**：跑一次就結束，不輪詢。

1. `ListJobs` 列出該 region 所有 job。API 不支援用 label 篩選，所以在程式端過濾 `managed-by == sep-engine`。`sep-cleaner` 自己沒有這個 label，不會被刪。
2. 對每個任務 job 看 `LatestCreatedExecution`：

   | 狀況 | 處理 |
   |---|---|
   | 沒有 execution，建立超過保留時間 | 刪除（孤兒） |
   | 沒有 execution，還在保留時間內 | 跳過（可能正要執行） |
   | 有 execution，`CompletionTime` 是空的 | 跳過（還在跑） |
   | 已結束（成功或失敗），超過保留時間 | 刪除 |

3. 印出掃描和刪除的數量。Cloud Logging 會自動收集 stdout。
4. `ListJobs` 失敗時回傳錯誤，`main` 用 `log.Fatalf` 結束，Cloud Run 會把這次 execution 標記為失敗。單一 job 刪除失敗只記錄，繼續處理下一個。

## G4：相依套件、Dockerfile、編譯確認

```bash
go get cloud.google.com/go/run@latest
go mod tidy
go build ./...
go vet ./...
```

**重要：`go.mod` 的 Go 版本會被拉高。** 驗證時 `cloud.google.com/go/run v1.25.0` 要求 `go 1.26.0`，`go get` 會自動把 `go.mod` 從 `go 1.25.0` 改成 `go 1.26.0`。兩個 Dockerfile 目前用 `golang:1.25-alpine`，不改的話 image 會建置失敗。要一併修改：

- `services/engine/Dockerfile`：`golang:1.25-alpine` → `golang:1.26-alpine`
- `services/cleaner/Dockerfile`：同上

這會影響 K8s 版的 CI（`.github/workflows/CI-Build.yaml` 用同樣的 Dockerfile），是預期內的變動，要告訴使用者。如果屆時最新版套件要求的 Go 版本不同，以 `go.mod` 實際的 `go` 那一行為準。

**完成條件**

| 檢查 | 預期 |
|---|---|
| `go build ./... && go vet ./...` | 無錯誤 |
| 不設 `PLATFORM`，照原本方式在本機跑 Engine | 行為和改寫前一樣（K8s 模式） |
| `PLATFORM=cloudrun` 且不設其他變數跑 Engine | 啟動失敗，訊息指出缺少 `GCP_PROJECT` 等設定 |
| `git status` | 只有預期的檔案變動，沒有 `specs/_reference` 以外的意外檔案 |

**選配：在本機用 ADC 測試 Cloud Run 模式**

需要先完成 T4（要有 `sep-task`）。這會在雲端建立真的 job，是使用者第一次看到任務在 Cloud Run 上跑，適合當作教學。使用者是專案 owner，權限足夠。

```bash
cd services/engine
PLATFORM=cloudrun GCP_PROJECT=<PROJECT_ID> GCP_REGION=asia-east1 \
TASK_SERVICE_ACCOUNT=sep-task@<PROJECT_ID>.iam.gserviceaccount.com \
SYSTEM_QUOTAS_JSON='{"demo-go":{"cpu":"1","memory":"512Mi"}}' \
ALLOWED_IMAGE_PREFIXES=us-docker.pkg.dev/cloudrun/container/ \
go run .
```

另開 terminal：

```bash
curl -X POST localhost:8080/api/run -H 'Content-Type: application/json' \
  -d '{"system_id":"demo-go","task_id":"local-001","image":"us-docker.pkg.dev/cloudrun/container/job:latest"}'
gcloud run jobs list --region asia-east1
```

測完記得刪除：`gcloud run jobs delete <job 名稱> --region asia-east1`。`us-docker.pkg.dev/cloudrun/container/job` 是 Google 官方的範例 job image。

## 可能遇到的問題

| 現象 | 原因和處理 |
|---|---|
| `CreateJob` 回 `PermissionDenied`，訊息提到 `iam.serviceaccounts.actAs` | 呼叫者沒有借用 `sep-task` 的權限。在 Cloud Run 上代表 T4 的 `engine_act_as_task` 沒 apply |
| `CreateJob` 回 `InvalidArgument`，提到 cpu 或 memory | 配額值不是 Cloud Run 允許的組合。`cpu: "1"`、`memory: "512Mi"` 是確定可用的值。Job 是否允許低於 1 vCPU 尚未實測，見規格 04 的待確認事項 |
| `CreateJob` 回 `InvalidArgument`，提到 name | job ID 不合規。`system_id` 上限是 40 字元，加上前綴和時間戳共 58 字元，預期在限制內；若仍被拒絕，依錯誤訊息調整 |
| `CreateJob` 提到無法讀取 image | 任務 image 在其他專案的私有 repo。本專案 repo 和公開 image 不應該發生；若發生，給 `sep-engine` 對該 repo 的 `roles/artifactregistry.reader` |
| 請求很慢或逾時 | `CreateJob` 通常幾秒內完成，已設 60 秒上限 |
